2 — What the product must do Full scope

One sentence

HotelApp is an operations layer for small hotels (15–80 rooms) — a guest sends a request without an app (QR + text/voice), AI turns it into tasks, staff acts on it, evidence is verified, the owner gets a briefing.

Who it is for

  • Small hotels, apart-hotels, hostels, apartment operators with staff but no proper ops software (they run on PMS/OTA, WhatsApp, spreadsheets, paper checklists).
  • Hotels undergoing renovation or operational upgrade — properties modernizing rooms, systems, or daily management.

Long-term intent: full management layer (guest services, housekeeping, maintenance, operations, finance, reporting) — global path, not a single-purpose tool. The hackathon build proves one end-to-end chain as the first vertical slice.

6 — The 9 blocks as they should be Proposed structure

Each block is a parallel work front — a group of tasks with a clear owner, entry point, and done criteria. A new teammate picks one block, reads its entry point, and starts without needing the full codebase in their head.

A

Guest Entry

QR → room page → text/voice → language
DoneNo new issue needed

Guest opens in-room QR, lands on room page, sends text or voice (mic 45s), sees language detection, edits transcript before Send.

What is done
  • /r/[room] + /api/guest/message + /api/guest/transcribe (muse-voice-transcribe-1.0)
  • MOCK/LIVE, hint "Check and fix, then Send", privacy (no history leak)
  • Responsive 375→1440, mic blocked handling, WAV 24kHz
What remains (if time)
  • Multi-room smoke test (/r/305), 2000-char boundary, phone HTTPS test
  • No new block issue — covered by existing ANT-6,7,10,11,12
B

AI Triage & Routing

1 message → N tasks (dept, priority, confidence)
DoneVerify, not build

AI reads guest text, splits multi-intent ("leak + towels" → 2 tasks), assigns department/priority/confidence, returns validated tasks.

What is done
  • muse-spark-1.3 via https://api.meta.ai/v1, temp 0.2, JSON with markdown guard
  • validateTasks() + mockTasks() fallback, LIVE verified (ANT-7)
What remains
  • Edge cases: unclear → front_desk/low, 502/503 UX, priority tuning (medium vs low)
  • Add 2 cases to DEVLOG before submission — no new issue required
C

Task Engine

Store, filter, sort — the spine
Done (demo)Demo-only store

Every task persisted, filterable by room/dept/ids, sorted urgent→newest, not lost between shifts.

What is done
  • store.ts: .data/tasks.json, atomic tmp→rename, withLock, isStoredTask, poll by IDs
  • GET /api/tasks + DELETE reset
Known limitation
  • File store, no DB — demo-only, lost on Vercel restart; mark as such in README
  • Post-hackathon: DB (Postgres/Supabase) + migration — not now

DoneDone

E

Proof & Vision — Photo Evidence

Staff photo → AI markers + confidence → supervisor queue
Not in LinearJury-critical

What it must do: after work, staff uploads a photo (bed, towels, fixed leak). AI checks the photo, returns markers: bed_ready, towels_present, visible_damage, cleanliness_issue — each with confidence. If uncertain, flags for supervisor.

Contract (already defined): markers + confidence + uncertainty bool + needs_human_review — "AI marks for supervisor, not declares clean."

What exists outside Linear
  • Prompt template and expected markers — defined, not yet wired to code
  • Synthetic photo descriptions in demo data
What is needed
  • Upload on task card → POST /api/tasks/{id}/evidence
  • Vision API call + markers → stored on task
  • If low confidence → route to block F (supervisor)

Why it matters: this is where "one more Meta AI step" and "photo evidence verified, not just declared" live — high jury value. Without it, the chain stops at "Done" with no proof.

F

Human Control — Supervisor Review & History

Verify human, audit trail — no autonomous irreversible decision
Not in LinearCore promise

What it must do: supervisor sees uncertain tasks, approves or asks to redo with a reason. Every step is logged: who, what, when, model, approval.

What is needed
  • Supervisor queue (uncertain tasks)
  • Approve / Request redo + reason → status → verified
  • Timeline per task: received → tasked → evidenced → reviewed → briefed
Minimal jury version
  • Even a single supervisor view that lists "needs review" + approve button satisfies "human-in-loop" — do not skip entirely
  • Log model + time + status on every transition

Why it matters: the product promise is "AI suggests, human decides — no autonomous irreversible decision." Without this block, that promise is a sentence in docs, not in the product.

G

Manager Intelligence — Briefing

Verified events → concise, verifiable briefing
Not in LinearOwner-facing value

What it must do: turn verified tasks + evidence + approvals into a short briefing: 3–5 bullets + stats (counts, avg response), not a notification flood. Only verified events, each linkable to task/photo/approval.

What exists outside Linear
  • Briefing prompt + output format (hotel, period, verified_tasks → bullets + stats) — defined
  • Muse Spark via Meta AI API — same stack as triage
What is needed
  • Collect verified tasks for period
  • Call briefing model → render briefing page
  • Fallback: template list if API down — still useful

Why it matters: this is the "value for manager" that the hackathon scores. Without it, the product is guest→staff only — the owner story is missing.

8 — Can a new teammate onboard in 1 hour? Hiring test

Today: no — and here is exactly why

  • No map to read. Linear has no project, no block labels, no priorities, no due dates. A flat list of 8 Done issues under one epic. The full 9-step path is not visible.
  • No block to pick. All issues are Done or In Progress (epic). There is no Backlog block for Photo/Vision/Briefing — a newcomer cannot claim unassigned work.
  • No entry point per block. No issue links to the already-defined Vision/briefing prompts. A newcomer must reverse-engineer the design from files on disk.
  • No assignment signal. All issues have no assignee, no priority, no estimate. "What should I take?" has no answer in Linear.

What "yes" looks like

A new teammate opens Linear, sees 9 blocks in priority order, picks one (e.g., "E — Proof & Vision"), and within 30 minutes knows: the contract, the prompt, the demo data, the API shape, and the done criteria. They do not need the whole codebase in their head — just their block.

9 — Proposed solution Recommendation

Principle: structure, not scope change

Nothing proposed here changes product scope, tech stack, or existing code. It only makes the existing scope visible and ownable so the team can parallelize the last 5 days — and so a new teammate can contribute on day one.

The solution in three layers

LayerWhat it isWho it helpsEffort
1. One mapA single page that shows all 9 blocks, what's done vs missing, and where to start per block — readable in 10 minutes.Every teammate + newcomer + reviewerOne HTML doc (this file) + one brief Linear issue pointing to it
2. Visible backlogThe missing blocks (E, F, G, and H/I) created as Backlog issues in Linear — not started, just visible — with description, entry point, and done criteria.Owner (can prioritize) + teammates (can claim)4–5 new issues, 5 min each, no code
3. Block ownershipEach block gets a label (A–I), priority (P0/P1), and optionally an assignee. Priorities make the final sprint plannable: P0 = jury-critical, P1 = polish after P0.Team (parallel work) + owner (review)Retag existing issues + set priorities

Priority proposal for the final sprint

P0 — MustH (deploy), I (video+Devpost), plus minimal E→F→GWithout H/I there is no submission. Without at least a minimal E→G, the jury sees only Guest→Staff and misses Vision + briefing + human-in-loop — the highest-scoring differentiators.
P1 — ShouldFull E (Vision), F (supervisor queue), G (briefing page) if P0 is secureMoves the vertical slice from "working" to "complete."

The goal for Nov 4 is not "perfect guest→staff" — it is "one complete loop the jury can follow: guest → AI → staff → proof → review → briefing." Everything else is polish.
